# 知识建模图生成

帮助高校教师为课程创建完整的知识建模图。

## 任务目标

你的目标不是解释建模思路，而是直接产出可导入、可显示、可继续迭代的知识建模图 JSON。

默认要求：
- 严格符合 `references/schema.json`
- 面向导入、显示、解析和后续增量修改
- 所有字段名称、引用关系、坐标记录、连线属性都必须可直接落入建模图前端或导入链路

## 阅读入口

- 新建 JSON：先看 [结构约束与检查](#结构约束与检查) → [节点对象属性说明](#节点对象属性说明) / [连线对象属性说明](#连线对象属性说明) → [布局与连接点规则](#布局与连接点规则) → [步骤 6：执行校验脚本](#步骤-6执行校验脚本)
- 修改已有 JSON：先看 [前置说明](#前置说明) 的增量原则，再按上面同一链路执行
- 快速查枚举与映射：看 [快速参考](#快速参考)

## 关联文件

- `references/schema.json`
  - 最终输出的唯一结构基准
  - 需要确认根对象、字段名、必填项、类型、枚举值和对象层级时，优先看这个文件
- `scripts/validate_json.py`
  - 本技能的校验脚本
  - 生成结果后必须用它校验 schema 合法性和建模图业务约束
  - 只有校验通过，结果才算完成
  - 用法：`python3 /skills/relation-graph/scripts/validate_json.py /path/to/result.json`

使用顺序：
- 先按本 `SKILL.md` 理解任务口径和处理顺序
- 再以 `references/schema.json` 约束最终结构
- 修改已有 JSON 时，优先以用户提供的当前 JSON 为基准，不重建整图
- 输出前必须按 `references/schema.json` 和本文件中的结构、布局规则完成自检
- 产出 JSON 后必须用 `scripts/validate_json.py` 校验，通过后才算完成

## 术语约定

- 节点（`node`）：`nodes[]` 内对象
- 连线（`line`）：`lines[]` 内对象（本文件不再使用 `edge` 术语）
- 根对象：最外层 JSON 对象（包含 `rootId`、`nodes`、`lines`）
- 关系文本：连线的 `text` 字段

## 生成 JSON 建模图

将知识点和关系转换为符合规范的知识建模图 JSON。

> **提示**：如果是生成新的 JSON，先读取 [schema.json](references/schema.json) 确认结构，再根据本技能规则补齐语义、布局和连接点。

> **⚠️ 关键结构警告**（常见导入失败原因）：
> - 连线数组名必须是 `lines`，不能用 `edges`
> - 连线属性名必须是 `from` / `to` / `text`，不能用 `source` / `target` / `label`
> - 每条连线必须包含 `fromJunctionPoint`、`toJunctionPoint`、`showStartArrow`、`showEndArrow`
> - 节点 `data.startPostion.x` / `y` 必须与节点 `x` / `y` 完全一致

### 前置说明

**已有 JSON 文件处理：**

如果用户已经提供了 JSON 文件，尤其是文件名或语义上表示为“当前建模图.json”这类当前图谱文件，应默认理解为：用户希望在现有建模图基础上继续修改、补充和微调，而不是整图重建。

处理原则：
- 优先以用户上传的当前 JSON 作为基准数据
- 尽量保持现有节点、连线、坐标、颜色、形状、文本、`data` 等属性不变
- 只有新增或明确要求修改的节点、连线，才依据本技能规则重新计算或调整
- 对未被用户要求修改的内容，不要重排、不重算、不覆盖
- 新增节点和新增连线，应在原 JSON 基础上追加
- 如果只是局部调整，应尽量只影响局部区域，避免破坏用户已经手工优化过的位置关系
- 目标是让用户可以基于同一个建模图 JSON 持续迭代、多轮优化，而不是每次生成一份全新的布局

**生成新图与修改旧图的处理区别：**
- 新建 JSON：先看 `references/schema.json`
- 修改现有 JSON：先理解原图结构，再只做局部增量修改

## 必填信息

缺失时先追问：
- 课程名称或主题名称
- 核心知识点 / 根节点
- 主要下位知识点、步骤、案例或策略
- 节点之间的关系类型
- 是否已有当前建模图 JSON 需要继续修改

## 选填信息

有就吸收，没有也继续生成：
- 节点语义类别提示，如核心知识点、结构化知识框架、先决知识点、思政点
- 节点层级偏好，如左右展开、上下展开、中心放射
- 用户已有的颜色、尺寸、坐标、局部布局偏好
- 是否需要保留原图中的局部区域和既有连线风格

## 处理原则

### 1. 先结构，后布局

- 先保证 JSON 结构合法、字段名正确、引用关系完整
- 再处理节点位置、连接点、连线避让与整体观感
- 任何美观性优化都不能破坏结构可导入性

### 2. 先语义，后样式

- 节点颜色、知识类型、关系文本必须由节点和关系语义决定
- 不要为了视觉对称或形式统一随意改写语义
- 颜色表达语义层次，真实形状表达知识类型，这是两套独立维度，不要混用

### 3. 先增量，后重排

- 只要用户给了当前 JSON，就默认优先做增量修改
- 除非用户明确要求重构布局，否则不要重排整图

### 4. 先校验，再定稿

- 生成结果后必须运行 `scripts/validate_json.py`
- 若校验失败，不能直接交付失败 JSON，必须继续修正直到校验通过
- 若失败原因是节点间距不足、局部重叠或高密度布局拥挤，应优先整体放大层间距、同层间距或局部偏移后重新校验
- 不要只修一条报错就结束，应持续回流校验，直到整份 JSON 返回 `VALID`

## 设计要点

1. 知识点挖掘必须全面
   - 必须覆盖与后续项目化教学课程紧密关联的知识组块，不要只抽取零散名词
2. 陈述性知识点后优先列出范例
   - 对理论性强、抽象度高、理解门槛高的陈述性知识点，后面应尽量补充对应范例知识点
   - 范例知识点优先使用 `data.type=6`
3. 使用颜色标注语义层次
   - 核心知识点标红
   - 核心的结构化知识框架标蓝
   - 先决知识点标绿
4. 使用树状结构
   - 整体应以树状结构、放射结构或思维导图式层级展开，清楚呈现知识点之间的逻辑关系
5. 使用规范关系连接
   - 优先使用 `支持`、`具有特征`、`包含`、`步骤包含`、`是前提`、`关键点包含`、`并列`、`定义`、`具有属性`、`是一种`、`组成`、`构成`
6. 确保关键内容一致性
   - 所有核心知识点、先决知识点、课程思政点都要在知识建模图中体现
   - 课程思政点若出现，也必须按其实际内容归入现有 `data.type` 分类，不单独扩展新类型
7. 范例要具体
   - 范例知识点可以是案例、视频、图片、参考书、作品片段或其他具体资源，不要只写空泛的“案例分析”

## 生成步骤

### 步骤 1：判断是新建还是修改

- 如果用户提供了现有 JSON，按增量修改处理
- 如果用户没有提供现有 JSON，按新建处理

### 步骤 2：确定语义结构

- 识别根节点、核心知识点、知识框架、先决知识、程序性步骤、案例、策略、思政点
- 识别关系语义，如 `包含`、`组成`、`步骤包含`、`是前提`、`是范例`、`支持`

### 步骤 3：确定节点与连线属性

- 节点属性、连线属性、`data.type`、颜色和连线参数按 [schema.json](references/schema.json) 与本文件相关章节处理
- 字段级口径以 [节点对象属性说明](#节点对象属性说明) 和 [连线对象属性说明](#连线对象属性说明) 为准

### 步骤 4：计算布局

- 坐标、间距、对称分布、连接点和防交叉按本文件“布局与连接点规则”章节处理
- 对高密度区域要预留冗余空间，优先保证节点间距，再考虑局部紧凑
- 若节点数较多、层级较深或混合布局容易碰撞，应主动放大 `x/y` 间距，不要贴着最小值生成

### 步骤 5：输出前检查

- 先做结构检查：先看 [schema.json](references/schema.json)，再看 [结构约束与检查](#结构约束与检查)
- 再做布局检查：看 [布局与连接点规则](#布局与连接点规则)

### 步骤 6：执行校验脚本

- 生成 JSON 后必须运行：`python3 src/skills/relation-graph/scripts/validate_json.py path/to/result.json`
- 只有脚本返回 `VALID`，结果才算完成
- 若脚本报节点间距不足，应回到布局阶段重新扩张画布与层间距，而不是仅做局部微调

## 输出要求

最终输出应是知识建模图 JSON，不要输出解释性大段说明来替代结果。

若用户要求附带说明，可在 JSON 之后补充极简说明，但不能省略最终 JSON。

## 结构约束与检查

若本章节与 `references/schema.json` 有冲突，一律以 `references/schema.json` 为准。

### 生成前后的结构约束

首要目标：生成出来的 JSON 必须可导入、可显示、可解析。

在满足结构可用之前，不要优先追求更美观的连接线或布局。任何坐标优化、连接点优化，都不能破坏 JSON 的结构合法性。

### 硬性要求

1. 严格使用 `schema.json` 定义的 JSON 结构
   - 根对象只能使用：`rootId`、`datetime`、`nodes`、`lines`
   - 连线数组名必须是 `lines`，不能写成 `edges`
   - 连线属性必须使用 `from`、`to`、`text`，不能写成 `source`、`target`、`label`
2. 禁止杜撰属性、禁止混入其他图库格式
   - 不要参考其他流程图、关系图库、思维导图库的字段命名习惯
   - 不要输出本规范未定义、且无法确定被支持的字段
   - 如果不确定某个字段是否支持，宁可不加，也不要臆造
3. 关键字段必须完整
   - 节点必须有：`id`、`text`、`x`、`y`、`data.type`
   - 连线必须有：`id`、`from`、`to`、`text`
   - 为保证导入后可正常显示，连线还必须明确：`fromJunctionPoint`、`toJunctionPoint`、`showStartArrow`、`showEndArrow`
4. 引用必须有效
   - `rootId` 是根对象标识，不与节点 `id` 复用
   - 每条连线的 `from`、`to` 必须都能在 `nodes[].id` 中找到
   - 所有 `id` 不能重复
   - `rootId` 必须使用 `root-随机字符串` 格式
   - 节点 `id` 必须使用 `node-随机字符串` 格式
   - 连线 `id` 必须使用 `line-随机字符串` 格式
5. 节点坐标字段必须自洽
   - `data.startPostion.x` 必须与节点 `x` 一致
   - `data.startPostion.y` 必须与节点 `y` 一致
6. 生成后必须先做结构验证，再做布局验证
   - 先检查 JSON 结构、字段名、字段完整性、引用关系是否正确
   - 确认结构可用后，再检查节点重叠、连线交叉、连接点协调性

### 结构禁止输出字段对照表

| 禁止输出 | 必须改为 | 原因 |
|:---------|:---------|:-----|
| `edges` | `lines` | 本技能连线数组固定使用 `lines` |
| `source` | `from` | 本技能连线起点字段固定使用 `from` |
| `target` | `to` | 本技能连线终点字段固定使用 `to` |
| `label` | `text` | 本技能关系文本字段固定使用 `text` |
| 其他外部图库专用字段 | 本规范已定义字段 | 禁止混入其他图库结构，避免导入失败 |

### 语义驱动的渲染约束

节点颜色、真实形状、知识类型、关系文本都必须由节点内容与实际语义决定，不能为了美观或对称随意指定。

1. 节点语义颜色必须匹配节点语义（仅指 `borderColor` / `fontColor`）
   - 核心知识点：红色 `#FF0000`，图形边线和字体均标红
   - 核心的结构化知识框架：蓝色 `#00B0F0`，图形边线和字体均标蓝
   - 先决知识点：绿色 `#00B050`，图形边线和字体均标绿
   - 普通知识点：黑色 `#000000`，图形边线和字体均标黑
   - `fontColor` 与 `borderColor` 必须完全一致
   - 节点背景色 `color` 固定为 `#ffffff`，不用于语义表达
2. 节点形状规则
   - 节点真实形状由 `data.type` 决定
   - 根节点也不例外，根节点真实形状同样由 `data.type` 决定，不因其是根节点而单独改形
3. `data.type` 必须匹配知识内容本身
   - 概念、定义、原理：`2`
   - 步骤、流程、操作方法：`3`
   - 学习方法、选择策略、分析策略：`5`
   - 案例、示例、范例：`6`
   - `data.type` 只能使用以上 4 种取值
   - 若内容属于思政点，也必须按其实际表达内容归入以上 4 类之一，不能单独扩展新的 `data.type`
4. 关系文本必须反映真实语义关系
   - 优先使用界面中受支持的关系词，例如：`支持`、`具有特征`、`内容包含`、`步骤包含`、`是前提`、`关键点包含`
   - 若这些关系词不足以准确表达语义，也允许使用更适配的描述文字
   - 关系文本的首要原则是语义准确，其次才是与常用关系词保持一致

- 是否出现了本规范未定义、无法确认支持的杜撰属性

## 布局与连接点规则

### 画布坐标系说明

整个画布是以中心点 `(0, 0)` 为原点，向四周无限延伸的无边区域。

### 坐标方向

- 原点 `(0, 0)` 为中心点
- 向左移动：`x` 减小
- 向右移动：`x` 增大
- 向上移动：`y` 减小
- 向下移动：`y` 增大
- 中心点左上：`(-x, -y)`
- 中心点左下：`(-x, +y)`
- 中心点右上：`(+x, -y)`
- 中心点右下：`(+x, +y)`

### 节点定位

- 节点位置由 `x`、`y`、`width`、`height` 决定
- 节点中心点 = `(x + width/2, y + height/2)`
- `width`、`height` 需要根据节点文字内容自适应生成

### 布局原则

- 核心知识点放置在画布中心附近
- 子知识点按层级向外延伸分布
- 节点绝对不能重叠，连接线尽量避免交叉

### 核心约束条件

#### 1. 节点间距

- 任意两个节点之间至少保持 `18px` 间距
- 必须结合节点 `x`、`y`、`width`、`height` 计算，不能只看中心点

#### 2. 节点重叠计算规则

关键原则：计算子节点坐标时，必须从源节点的边界开始计算，而不是从源节点的 `x/y` 坐标开始。

假设父节点 `A(xA, yA, width: wA, height: hA)`，子节点 `B(width: wB, height: hB)`：

- 右侧子节点：
  - `A` 的右边界 = `xA + wA`
  - `B.x >= (xA + wA) + 间距`
- 左侧子节点：
  - `B.x + wB <= xA - 间距`
- 下方子节点：
  - `B.y >= (yA + hA) + 间距`
- 上方子节点：
  - `B.y + hB <= yA - 间距`

#### 3. 连接线交叉预防

- 相邻层级的节点尽量采用不同的 `y` 值或 `x` 值偏移
- 同一父节点的多个子节点按顺序错开排列
- 必要时增大层间距或节点间距

#### 4. 跨父节点子节点防交叉

- 当多个父节点的子节点位于同一层级时，需要整体考虑所有子节点布局
- 不同父节点的子节点要在 `y` 方向上错开，避免交叉

参考约束：

```text
父节点A的子节点范围: yA_min ~ yA_max
父节点B的子节点范围: yB_min ~ yB_max
需要满足:
yA_max + 间距 < yB_min
或
yB_max + 间距 < yA_min
```

#### 5. 同父节点多级子节点防重叠

- 当同一个父节点的多个子节点又连接到下一级子节点时，这些孙节点应在 `x` 方向上错开分布
- 不能让所有孙节点都处于同一个 `x` 位置

#### 6. 空间预留

- 生成前先估算所有节点所需总空间
- 根据子节点数量和层级深度预留足够区域
- 避免后续节点没有足够空间摆放
- 对节点数较多的图，不要以“刚好不重叠”为目标，应预留额外冗余，避免校验阶段出现边界碰撞

### 对称布局计算

#### 上下连接的对称计算

```text
源节点A: x=0, y=0, width=200, height=60
子节点在A右侧时，应从 A 的右边界开始计算:
第一个子节点 x = 0 + 200 + 间距
```

#### 左右连接的对称计算

```text
源节点A: x=0, y=0, width=200, height=60
子节点在A下方时，应从 A 的底部边界开始计算:
第一个子节点 y = 0 + 60 + 间距
```

#### 错误示例

```text
源节点A: x=0, width=200
错误: 子节点x = 0 + 150
正确: 子节点x = 0 + 200 + 150
```

#### 正确示例

```text
父节点A: x=0, y=0, width=200, height=60
2个子节点在右侧:
- 起始x = 0 + 200 + 50 = 250

父节点A下方有2个子节点:
- 起始y = 0 + 60 + 50 = 110
```

### 子节点布局规则

#### 单个子节点

- 上下连接：可放在上下位置，连接线垂直
- 左右连接：可放在左右位置，连接线水平

#### 多个子节点，上下连接

- 需要在 `x` 方向均匀分布，同时 `y` 方向留出层间距
- 尽量保持与父节点中心对称

计算公式：

```text
父节点中心: centerX = x + width/2
子节点数量: n
子节点总宽度: totalWidth = sum(width) + (n - 1) * spacing
起始x: startX = centerX - totalWidth/2
```

#### 多个子节点，左右连接

- 需要在 `y` 方向均匀分布，同时 `x` 方向留出层间距
- 尽量保持与父节点中心对称

计算公式：

```text
父节点中心: centerY = y + height/2
子节点数量: n
子节点总高度: totalHeight = sum(height) + (n - 1) * spacing
起始y: startY = centerY - totalHeight/2
```

#### 对称布局示例

```text
父节点A: x=0, y=0, width=200, height=60, centerX=100, centerY=30
有3个子节点: width=140, height=45, spacing=30

方案1:
- 保持 y 一致，x 均匀分布

方案2:
- 保持 x 一致，y 均匀分布
```

### 多层布局计算

- 第二层节点：以第一层节点为基准计算坐标
- 第三层节点：以第二层节点为基准计算坐标
- 以此类推，确保每一层都不与相邻层重叠

### 连接点优化目标

连接点选择时，按以下优先级综合考虑：

1. 结构合法：必须输出 `fromJunctionPoint`、`toJunctionPoint`
2. 方向正确：连线出发方向与目标节点相对方位一致
3. 局部顺畅：尽量减少折返、贴边滑行、过长绕行
4. 多关系均匀分布：同一节点同一侧的多条关系不能全部挤在中点
5. 整体更协调：尽量减少交叉，保持主干结构清晰

### 二维坐标系下的相对方位判断

设起始节点 `A(xA, yA, widthA, heightA)`，目标节点 `B(xB, yB, widthB, heightB)`。

```text
centerA = (xA + widthA/2, yA + heightA/2)
centerB = (xB + widthB/2, yB + heightB/2)

dx = centerB.x - centerA.x
dy = centerB.y - centerA.y
```

判断规则：

- `|dx| >> |dy|`：以左右关系为主
- `|dy| >> |dx|`：以上下关系为主
- `|dx|` 与 `|dy|` 接近：视为斜向关系

### 连接点候选与择优

#### 正向关系的基础候选

| B 相对 A 的位置 | 优先候选 |
|:-----------------|:---------|
| 正右 | `right -> left` |
| 正左 | `left -> right` |
| 正上 | `top -> bottom` |
| 正下 | `bottom -> top` |

#### 斜向关系的候选组合

| B 相对 A 的位置 | 候选方案 1 | 候选方案 2 |
|:-----------------|:-----------|:-----------|
| 右上 | `right -> bottom` | `top -> left` |
| 右下 | `right -> top` | `bottom -> left` |
| 左上 | `left -> bottom` | `top -> right` |
| 左下 | `left -> top` | `bottom -> right` |

#### 择优规则

- 哪个方案更符合当前主方向
- 哪个方案与现有连线交叉更少
- 哪个方案让同一侧多条关系分布更均匀
- 哪个方案更少穿越密集节点区域

如果两个方案差异不明显，优先选择更符合主方向的那个。

### 同一节点多条关系的连接点分布规则

关键原则：同一节点同一侧的多条连线，不能都连接到该侧的中点。

处理方式：

1. 先按连线方向分组：`left`、`right`、`top`、`bottom`
2. 组内排序
   - 左右侧分组：按目标节点 `centerY` 排序
   - 上下侧分组：按目标节点 `centerX` 排序
3. 在该侧边界上按顺序均匀分配锚点

### 调优规则

如果某条边单独看方向没问题，但放到整体图中不协调，则按以下顺序调优：

1. 先调整连接点组合
2. 再调整同侧锚点顺序
3. 必要时才调整节点布局

### 典型案例

#### 案例 1：B 在 A 左边

```text
A.left -> B.right
```

#### 案例 2：B 在 A 左下

```text
候选1: A.left -> B.top
候选2: A.bottom -> B.right
若 A 左侧已很拥挤，则优先候选2
```

#### 案例 3：B 在 A 右上

```text
候选1: A.right -> B.bottom
候选2: A.top -> B.left
若 A.right 已拥挤，则优先候选2
```

#### 案例 4：A 同时连接多个右侧子节点

```text
A.right 不能所有边都从中点发出
应按子节点从上到下排序后分配多个锚点
```

#### 案例 5：两个方案方向都对，但一个更协调

```text
优先选择与其他线交叉更少、边上更均匀的方案
```

### 布局检查清单

- 节点不能重叠
- 节点间距至少 `18px`
- 连接线尽量避免交叉
- 同一节点同一侧多条关系不能共用一个中点
- 连线方向应与节点相对位置基本一致
- 若任一项不满足，必须重新布局并再次执行 `validate_json.py`

### 节点形状说明

- 真正形状由 `data.type` 决定
- 根节点与普通节点遵循同一规则，根节点形状不单独特殊处理

### 常用关系文本

- `支持`
- `具有特征`
- `包含`
- `步骤包含`
- `是前提`
- `关键点包含`
- `并列`
- `定义`
- `具有属性`
- `是一种`
- `组成`
- `构成`

说明：
- 上述关系词是优先推荐使用的常见关系文本
- 连线文本不在校验脚本中做强枚举校验
- 若业务语义更适合使用其他描述文字，也允许输出更贴切的关系文本

### 程序性知识标注规则

- 下级知识点为步骤或流程：标识为程序性知识
- 下级知识点不是步骤或流程：优先标识为陈述性知识
